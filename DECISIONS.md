# Decisions and trade-offs

Each entry gives the decision, the reason, and what it costs.

## Architecture

**Layered Spring Boot: controller, service, repository.**
* Controllers are thin and only handle HTTP and DTOs.
* Services hold every business rule and return DTOs, so JPA entities never reach a controller or the JSON output.
* Hand-written mappers in `web/mapper` keep the conversion visible.
* Cost: services depend on the DTO package. A larger system might add a separate service model.

**Java 21, Spring Boot 3.3.13, Gradle Kotlin DSL.** The PRD allows Java 17 or 21. Java 21 is the current LTS, and records keep DTOs short.

**PostgreSQL 16 at runtime, H2 in tests, Flyway for the schema.**
* PostgreSQL is a production database and runs easily in Docker Compose.
* Flyway makes the schema versioned and repeatable. Hibernate only validates it, so a mismatch between entities and schema stops the app at startup.
* H2 in PostgreSQL mode keeps tests fast and free of Docker.
* Cost: the migrations must avoid database-specific SQL, and H2 is not a perfect PostgreSQL copy. Every write path was also checked by hand against PostgreSQL in Docker.

**UUID ids generated by the application.** UUIDs cannot be guessed or counted, need no database sequence, and let seed data use fixed, readable ids. Cost: 16-byte keys, which is no concern at this size.

## Security approach

**Stateless JWT with two roles, ADMIN and OPERATIONS.**
* `POST /api/auth/login` checks the BCrypt hash and returns an HS256 token.
* The token carries the username, the role and an expiry, with 480 minutes by default.
* `JwtAuthFilter` validates the token on each request without a database lookup.
* Stateless tokens suit a REST API and Docker scaling, and they are easy to try from Swagger.
* Cost: a token stays valid until it expires, even if the user is removed. There is no logout, refresh or revocation list.

**Role rules sit in one place, `SecurityConfig`, following the plan's role matrix.**
* Only ADMIN creates treks and checkpoints and changes trek status. That shapes the trek plan.
* Both roles read data, register participants and change their status, record check-ins, and acknowledge or resolve alerts. That is the daily operations work.
* Login, `/api/health`, Swagger and the API docs are public. Everything else needs a token.

**Login does not reveal which usernames exist.** An unknown user and a wrong password get the same message. For an unknown user, the service still runs a BCrypt comparison against a throwaway hash, so response time does not give it away.

**Secrets come from the environment.**
* `JWT_SECRET` has no default in the default profile. `JwtProperties` validates it at startup and stops the app if it is missing or shorter than 32 characters.
* Real values live in the git-ignored `.env`. Only `.env.example` is committed, with empty secrets.
* The seed passwords are demo values documented in the README.

## Scheduler approach

**`@Scheduled` with a fixed delay, in the application itself.**
* `DelayDetectionScheduler` only calls `DelayDetectionService.detectDelays()`.
* Fixed delay means the next run starts a set time after the previous one ends, so runs never overlap.
* The interval and an on and off switch come from configuration.
* This is the simplest correct choice, and the PRD leaves the approach open.
* Cost: it assumes one application instance. Several instances would each run the check. The duplicate guard below keeps that mostly harmless, but alerts could still be raised twice in a race. Running several instances would call for ShedLock or a job scheduler such as Quartz.

**The delay rule is evaluated from the data, not from missed runs.** Each run looks at the current state: overdue checkpoints with no check-in and no alert. If the scheduler was down for an hour, the next run catches up on its own.

**Time comes from an injected `Clock`.** Every service reads time from the `Clock` bean, never from `Instant.now()`. Tests use `Clock.fixed`, so the delay rule is tested at exact moments, including "exactly at the expected time is not yet late".

**A configurable grace period.** `DELAY_CHECK_GRACE_MINUTES`, default 0, delays the alert. In the field a few minutes late is normal, and the operator can tune this without a code change.

## Concurrency considerations

* **Duplicate check-ins.** The service checks for an existing check-in first and returns 409. Two requests can still pass that check together. The database unique constraint on participant and checkpoint then rejects the second insert, and the service turns that error into the same 409. The database is the final guard.
* **Duplicate alerts.** The delay check runs in one transaction on a single scheduler thread and skips any pair that already has an alert. With one instance, that is enough. A partial unique index on active alerts would also guard several instances. It was left out because H2 and PostgreSQL do not share that syntax.
* **Alert updates.** Acknowledge and resolve read the current status and change it in one transaction. Two users acting on the same alert at the same moment would both succeed, and the later write wins. There is no optimistic lock (`@Version`) yet. That is listed in `SELF_REVIEW.md`.
* **Notifications after commit.** The dispatcher listens with `@TransactionalEventListener(AFTER_COMMIT)`, so an alert that is rolled back is never announced.

## Search implementation

**JPA Specifications with paging and a sort whitelist.**
* `GET /api/participants` takes optional `trekId`, `status`, `name` and `phone` filters. Name matching ignores case and both name and phone match partially.
* Each filter in `ParticipantSpecifications` returns a condition or null. `Specification.where(...).and(...)` skips the nulls, so any mix of filters works without hand-built queries.
* `%` and `_` in input are escaped, so they match literally and cannot widen the search.
* Results are paged, 20 by default and at most 100. The JSON shape is `content`, `page`, `size`, `totalElements` and `totalPages`.
* Sorting is allowed only on `name`, `status`, `createdAt` and `updatedAt`. Anything else is a 400 that names the allowed fields. This keeps clients off internal columns.
* Trek and alert lists use plain paging. An unknown sort field there is also a 400.
* Cost: partial `LIKE '%x%'` matching cannot use an index. That is fine at this size, but large data would need full-text search.

## Status modeling

* Each status is a Java enum stored as text. A database `CHECK` limits each column to the enum values, and the text stays readable in SQL.
* The allowed transitions live in each service as a small map from a status to the set of statuses it may move to. Anything else is a 422. The maps are easy to read and to test. See `DOMAIN_MODEL.md` for the diagrams.
* Cross-entity rules use status:
  * A trek needs a checkpoint before it becomes `ACTIVE`.
  * A participant can go `ON_TREK` only while the trek is `ACTIVE`.
  * A check-in needs an `ACTIVE` trek.
  * `DROPPED` and `COMPLETED` participants cannot check in.
* **One alert per participant and checkpoint, in any status.** This is stricter than the plan's "one OPEN or ACKNOWLEDGED alert". With the plan's rule, an alert that ops resolve by hand ("spoke to them, they are fine") would be raised again on the next run, every minute, until a check-in came in.
* **A check-in resolves the open alert for its pair.** The plan's alert flow allows this. The participant has reported, so the alert has done its job. The user who recorded the check-in becomes the resolver.

## Configuration approach

* One `application.yml` with three profiles:
  * `default` is PostgreSQL from environment variables, used by Docker Compose.
  * `local` is PostgreSQL on localhost, for runs from an IDE.
  * `test` is in-memory H2 with the scheduler off.
* Behavior that can change without a code change: `JWT_SECRET`, `TOKEN_TTL_MINUTES`, `DELAY_CHECK_ENABLED`, `DELAY_CHECK_INTERVAL_MS`, `DELAY_CHECK_GRACE_MINUTES`, `NOTIFICATION_CHANNELS`, and the database settings.
* Settings are bound to validated `@ConfigurationProperties` records (`JwtProperties`, `DelayCheckProperties`, `NotificationProperties`), so a bad value fails at startup, not later.
* The database connection wait is 5 seconds instead of Hikari's 30, so `/api/health` reports a down database quickly.

## Notification design

* **An event and pluggable channels.**
  * The delay check publishes an `AlertCreatedEvent` for each new alert. The event carries plain values, not entities, so it is safe to use after the transaction ends.
  * `NotificationDispatcher` sends it to every `NotificationChannel` named in `NOTIFICATION_CHANNELS`.
  * `LogNotificationChannel` writes a warning line, which stands in for delivery. The PRD says real delivery is not required.
* **Adding a channel is one class.** Implement `NotificationChannel` as a Spring bean, give it a name such as `email`, and add the name to `NOTIFICATION_CHANNELS`. Nothing else changes.
* **One channel cannot break the others.** A failing channel is logged and the rest still run. Unknown channel names are reported at startup.
* Cost: delivery runs on the scheduler thread with no retry. A slow real channel would need an async executor or a message queue.

## Error handling

* Every error has one JSON shape, `ApiError`, with `timestamp`, `status`, `error`, `message` and `path`. Validation errors add an `errors` map from field to message.
* `GlobalExceptionHandler` maps exceptions to statuses: 400 for validation, malformed input and bad sort, 401, 403, 404, 405, 409 for conflicts and 422 for business rules.
* Security rejections never reach a controller, so `SecurityErrorHandler` writes the same shape for 401 and 403.
* Unexpected errors return a generic 500 message. The details go only to the log.

## API documentation and health

* springdoc generates the OpenAPI document. `OpenApiConfig` adds a bearer JWT scheme, so the Authorize button in Swagger UI sends the token. Login and health are marked as open.
* `GET /api/health` is public. It returns the application name, the version from Gradle build info, the database state and the time. It answers 503 when the database does not respond, which works for container health checks.
